## Receiving

SwissKnife can receive funds over Lightning (invoices, your Lightning Address, LNURL-pay, and Nostr Zaps) and on-chain Bitcoin.

### Lightning invoices

Generate a BOLT11 invoice for a specific amount:

- [`POST /v1/me/wallets/{wallet_id}/invoices`](https://api.numeraire.tech/docs#tag/me/POST/v1/me/wallets/{wallet_id}/invoices) — generate an invoice for the selected wallet.
- [`GET /v1/me/wallets/{wallet_id}/invoices`](https://api.numeraire.tech/docs#tag/me/GET/v1/me/wallets/{wallet_id}/invoices) and [`GET /v1/me/wallets/{wallet_id}/invoices/{id}`](https://api.numeraire.tech/docs#tag/me/GET/v1/me/wallets/{wallet_id}/invoices/{id}) — list and look up invoices for that wallet.

```bash
curl -X POST https://your-instance:3000/v1/me/wallets/<wallet-id>/invoices \
  -H 'Authorization: Bearer <jwt>' \
  -H 'Content-Type: application/json' \
  -d '{
    "amount_msat": 100000,
    "description": "Coffee",
    "expiry": 3600
  }'
```

Only `amount_msat` is required; `description` and `expiry` (seconds) are optional. The
account-scoped routes authorize access through the authenticated account and wallet path.

### Your Lightning Address

A Lightning Address (`username@your.domain`) lets anyone pay you using a human-readable identifier, the same way email works. The domain is configured per instance (see [Configuration](../configuration/index.mdx)).

- [`POST /v1/me/lightning-address`](https://api.numeraire.tech/docs#tag/me/POST/v1/me/lightning-address) — register your address (`username`).
- [`GET /v1/me/lightning-address`](https://api.numeraire.tech/docs#tag/me/GET/v1/me/lightning-address) — fetch your registered address.
- [`PUT /v1/me/lightning-address`](https://api.numeraire.tech/docs#tag/me/PUT/v1/me/lightning-address) — update it (toggle `active`, Nostr settings).

```bash
curl -X POST https://your-instance:3000/v1/me/lightning-address \
  -H 'Authorization: Bearer <jwt>' \
  -H 'Content-Type: application/json' \
  -d '{
    "username": "alice",
    "allows_nostr": true,
    "nostr_pubkey": "<hex-pubkey>"
  }'
```

Open **Identity → Lightning** to copy your registered address or its LNURL QR
code. When the instance has no public domain, the page explains which setting
your administrator needs to configure. Individual invoices are available in
**Receive**.

Lightning Addresses are account-level handles. SwissKnife routes incoming invoices to the
account's native-BTC wallet for the node's configured network; callers cannot select an
incompatible network or a non-BTC asset. Account ownership authorizes the `/v1/me` registration,
update, read, and delete routes.

### LNURL-pay

Each registered Lightning Address is served over LNURL-pay at well-known, unauthenticated endpoints that any LNURL-capable wallet can resolve:

- [`GET /.well-known/lnurlp/{username}`](https://api.numeraire.tech/docs#tag/lnurl/GET/.well-known/lnurlp/{username}) — returns the LNURL `payRequest` for the address.
- [`GET /lnurlp/{username}/callback`](https://api.numeraire.tech/docs#tag/lnurl/GET/lnurlp/{username}/callback) — returns an invoice for the requested amount.

Sender wallets use these endpoints when paying `username@your.domain`. Payment
integrations can follow the same flow to generate invoices and verify their settlement.

#### LUD-21 invoice verification

From SwissKnife 0.3.3, the callback response includes a `verify` URL implementing
[LUD-21](https://github.com/lnurl/luds/blob/luds/21.md). A payment integration can
use this URL to check whether the invoice has settled without access to the
recipient's Lightning node.

Send a `GET` request to the returned URL, which points to
`/lnurlp/{token}/verify`. Use the URL as returned; it needs no JWT or API key.
Before settlement, the response contains the original BOLT11 invoice in `pr`:

```json
{
  "status": "OK",
  "settled": false,
  "preimage": null,
  "pr": "lnbc..."
}
```

After settlement, `settled` is `true` and `preimage` contains the hex-encoded
payment preimage. This also works for payments settled through SwissKnife's
internal ledger. An invalid or unknown token returns HTTP 200 with
`{"status":"ERROR","reason":"Not found"}`; clients must inspect `status`.

### Nostr (NIP-05 and Zaps)

When a Lightning Address is registered with `allows_nostr: true` and a `nostr_pubkey`, SwissKnife also serves NIP-05 verification and enables Lightning Zaps for that identifier:

- [`GET /.well-known/nostr.json`](https://api.numeraire.tech/docs#tag/nostr/GET/.well-known/nostr.json) — maps the username to its Nostr public key (hex), satisfying [NIP-05](https://github.com/nostr-protocol/nips/blob/master/05.md).

### On-chain Bitcoin address

For self-hosted CLN and LND setups, SwissKnife includes an integrated on-chain wallet. Generate a deposit address to receive on-chain Bitcoin:

- [`POST /v1/me/wallets/{wallet_id}/bitcoin/addresses`](https://api.numeraire.tech/docs#tag/me/POST/v1/me/wallets/{wallet_id}/bitcoin/addresses) — get a deposit address for the selected wallet.

```bash
curl -X POST https://your-instance:3000/v1/me/wallets/<wallet-id>/bitcoin/addresses \
  -H 'Authorization: Bearer <jwt>' \
  -H 'Content-Type: application/json' \
  -d '{}'
```

The returned address stays the same until it is used on-chain, after which a new one is generated. You can optionally request a specific script `type` (`p2pkh`, `p2sh`, `p2wpkh`, or `p2tr`); when omitted, the instance default (`bitcoin_address_type`, defaults to `p2wpkh`) is used. The account-scoped route enforces wallet ownership. See the [on-chain wallet](#on-chain-bitcoin-wallet) section below for managing addresses.

For one sale, send `{"dedicated": true}` in the address request. Each successful call
allocates a different address and returns `dedicated: true`. Retain that address
with your order. The wallet can continue receiving ordinary deposits on its existing
address. To recover deposits after a disconnect, query
`GET /v1/me/wallets/{wallet_id}/invoices?bitcoin_address=<address>`. Each matching
invoice includes its Bitcoin output and settlement status.

### Merchant checkout

Open **Point of sale** from a Bitcoin wallet, enter the sale amount in whole sats,
and optionally enter an order reference. The customer can scan one QR code for
Lightning or on-chain Bitcoin when both methods are available. Checkout shows
the method if only one provider operation succeeds.

A detected on-chain payment can appear before it confirms when the provider
reports mempool deposits. Checkout counts a payment toward the sale after it
settles. Multiple deposits to the sale address can cover one order. The cashier
can open the payment details or start the next sale.

The current sale survives a reload in the same browser tab when session storage
is available. Sound and vibration are optional on each device. A request is shown
for up to 15 minutes. Closing it or letting it expire leaves the Bitcoin address
valid. Late deposits remain visible in wallet activity.

## Sending

A single endpoint handles all outgoing payments. The recipient `input` can be a BOLT11 invoice, an LNURL, or a Lightning Address; payments to another wallet on the same instance are settled instantly through the internal ledger.

- [`POST /v1/me/wallets/{wallet_id}/payments`](https://api.numeraire.tech/docs#tag/me/POST/v1/me/wallets/{wallet_id}/payments) — send a payment from the selected wallet.
- [`GET /v1/me/wallets/{wallet_id}/payments`](https://api.numeraire.tech/docs#tag/me/GET/v1/me/wallets/{wallet_id}/payments) and [`GET /v1/me/wallets/{wallet_id}/payments/{id}`](https://api.numeraire.tech/docs#tag/me/GET/v1/me/wallets/{wallet_id}/payments/{id}) — list and look up payments for that wallet.

```bash
# Pay a BOLT11 invoice
curl -X POST https://your-instance:3000/v1/me/wallets/<wallet-id>/payments \
  -H 'Authorization: Bearer <jwt>' \
  -H 'Content-Type: application/json' \
  -d '{ "input": "lnbc1..." }'

# Pay a Lightning Address (amount required; the input has none)
curl -X POST https://your-instance:3000/v1/me/wallets/<wallet-id>/payments \
  -H 'Authorization: Bearer <jwt>' \
  -H 'Content-Type: application/json' \
  -d '{ "input": "bob@example.com", "amount_msat": 100000, "comment": "Thanks!" }'
```

Notes on the request body:

- `input` is required. For a BOLT11 invoice that already encodes an amount, omit `amount_msat`; for an LNURL or Lightning Address, supply `amount_msat`.
- `comment` is optional and is shown to the recipient for LNURL payments.

The account-scoped send and list routes enforce ownership of the wallet in the path.

:::tip
Admins can send on behalf of any wallet using the non-`/me` endpoint [`POST /v1/payments`](https://api.numeraire.tech/docs#tag/payments/POST/v1/payments) with a `wallet_id`. There is no default wallet fallback; the wallet selector is required.
:::

### Background Lightning payments

An integration can submit an external BOLT11 invoice, LNURL-pay request or Lightning
Address and release its HTTP connection while the node routes the payment. Generate a
UUID for each payment the user approves and save it with the original request before
sending. Reuse that UUID and the same input, amount, comment and fee ceiling on a retry.

```http
POST /v1/me/wallets/{wallet_id}/payments/submissions
Authorization: Bearer <jwt>
Content-Type: application/json

{
  "idempotency_key": "ab11ad05-5c90-4c75-b908-5a5c352971dd",
  "input": "<external BOLT11 invoice>",
  "maximum_fee_msat": 5000
}
```

SwissKnife resolves the invoice, validates its amount and expiry, and commits the wallet
reservation before returning `202 Accepted`. Amountless invoices and LNURL payments
require `amount_msat`. The routing fee ceiling is the lower of `maximum_fee_msat` and
the configured provider limit. The response includes the payment, its execution state,
and a `status_url`. The same URL appears in the `Location` header.

| State | Wallet and provider behavior |
| --- | --- |
| `accepted` | The database holds the payment and its reservation. A worker can claim it. |
| `processing` | A worker claimed the command. The node may still be routing, or SwissKnife may be waiting for a definitive result. |
| `settled` | The payment completed. The final wallet debit includes the actual fee. A validated LNURL success action is available on the payment. |
| `failed` | The node reported a definitive failure. SwissKnife released the reservation. |

Read `status_url` with the same wallet authorization after a reconnect. Account events
`payment.accepted`, `payment.processing`, `payment.settled` and `payment.failed`
prompt clients to refresh that resource. A lost submission response can be recovered
by repeating the original POST. Changing its payload under the same key returns
`409 Conflict`. Deleting a terminal payment leaves its key unavailable for reuse.

A restart picks up unclaimed commands. Once a Lightning payment has been dispatched,
SwissKnife checks the original hash with the provider even when no new event arrives.
Background checks run 30 seconds after the preceding pass finishes. A pending or missing
provider record keeps the reservation in place. Confirmed failure releases it, and
confirmed settlement charges the actual amount and fee. Poll the original status URL
to see that result. A crash between the durable claim and the node call can leave a payment in
`processing` without a matching node record. Ask the operator to reconcile the hash
and the reservation before authorizing another attempt.

Operators can use `POST /v1/payments/submissions` with `wallet_id` and
`write:transaction`. Reading the corresponding status requires `read:transaction`.
A destination issued by this installation returns `422` with the code
`internal_transfer_required` before funds are reserved. The wallet's ordinary payment
endpoint settles such transfers internally.

## Fee estimates and pending payments

`POST /v1/me/wallets/{wallet_id}/payments/fee-estimate` accepts the same payment input as sending. Lightning quotes distinguish an optional estimated fee from the hard maximum enforced by the provider. On-chain quotes temporarily prepare and release a transaction; the actual send prepares again, so its final fee can differ. Internal transfers quote zero fees.

An HTTP success response can contain a pending payment. If a Lightning send or on-chain broadcast has an unknown outcome, SwissKnife keeps its reservation instead of making the funds spendable again. A later node result can settle or fail the payment; some unresolved cases need manual reconciliation. Do not resend simply because the original HTTP request timed out.

### Trying a failed payment again

After a payment reaches `Failed`, an administrator can delete its record from
the administrative transaction table or with `DELETE /v1/payments/{id}`
(`write:transaction` permission), then submit another payment through the normal
send flow. Use an invoice that is still valid, or request a new one. Pending
payments cannot be deleted; wait for their outcome before trying again.

## On-chain Bitcoin wallet

The on-chain wallet (available for self-hosted CLN and LND) supports address management, wallet synchronization, and transaction preparation before broadcast.

### Generating and managing addresses

- [`POST /v1/me/wallets/{wallet_id}/bitcoin/addresses`](https://api.numeraire.tech/docs#tag/me/POST/v1/me/wallets/{wallet_id}/bitcoin/addresses) — generate/return a deposit address for the selected wallet (see [On-chain Bitcoin address](#on-chain-bitcoin-address) above).
- [`GET /v1/bitcoin/addresses`](https://api.numeraire.tech/docs#tag/bitcoin-addresses/GET/v1/bitcoin/addresses) — list Bitcoin addresses (with filtering and pagination).
- [`GET /v1/bitcoin/addresses/{id}`](https://api.numeraire.tech/docs#tag/bitcoin-addresses/GET/v1/bitcoin/addresses/{id}) — look up a single address.
- [`DELETE /v1/bitcoin/addresses`](https://api.numeraire.tech/docs#tag/bitcoin-addresses/DELETE/v1/bitcoin/addresses) and [`DELETE /v1/bitcoin/addresses/{id}`](https://api.numeraire.tech/docs#tag/bitcoin-addresses/DELETE/v1/bitcoin/addresses/{id}) — delete addresses.

Each address record reports its `address`, `address_type`, and a `used` flag indicating whether it has already received funds on-chain. The non-`/me` administrative list/get routes require `read:btc_address`, and administrative generation/deletion requires `write:btc_address`.

### Wallet sync and transaction preparation

SwissKnife synchronizes on-chain wallet state with your node so deposits are detected and balances stay current. Outgoing on-chain spends are **prepared before broadcast**, giving you a safe path to construct and review a transaction. On-chain spends are sent through the same payment flow as Lightning: pass an on-chain destination to [`POST /v1/me/wallets/{wallet_id}/payments`](https://api.numeraire.tech/docs#tag/me/POST/v1/me/wallets/{wallet_id}/payments).

:::note
The on-chain wallet requires a self-hosted Core Lightning or LND provider and the `bitcoin_address_type` setting. See the [Liquidity providers](../configuration/liquidity-providers.mdx) and [Configuration](../configuration/index.mdx) pages for setup.
:::

## Export a wallet statement

Open **Activity** for the selected wallet, choose **Export statement**, enter the first and last
UTC dates to include, and download the CSV. Administrators with transaction-read permission
can export from an individual wallet's detail page. The download covers all activity created
during those dates, including transactions on later pages of the activity table.

The account API accepts an inclusive `from` and exclusive `until` timestamp. For example,
to include all of March, pass midnight on March 1 and midnight on April 1.

```bash
curl --fail --get "https://your-instance/v1/me/wallets/$WALLET_ID/statement" \
  -H "Authorization: Bearer $TOKEN" \
  --data-urlencode "from=2025-03-01T00:00:00Z" \
  --data-urlencode "until=2025-04-01T00:00:00Z" \
  --output wallet-march.csv
```

The administrative endpoint is `GET /v1/wallets/{id}/statement` and requires `read:transaction`.
An empty interval with valid dates returns a file containing the headers.

| Columns | Meaning |
| --- | --- |
| `transaction_id`, `wallet_id`, `asset_id`, `network` | Stable identifiers and network for matching exports to API records. |
| `created_at_utc`, `payment_time_utc` | Creation time and recorded payment time. The payment time is empty until recorded. |
| `direction`, `ledger`, `status` | Invoices are `in` and payments are `out`. The ledger identifies Lightning, on-chain or internal activity. Status is current at export time. |
| `gross_amount_msat`, `fee_msat` | Integer millisatoshis. Incoming rows use the actual received amount when available and the requested amount otherwise. A blank amount or fee is unknown. Import these columns as text in spreadsheets that round long integers. |
| `description` | User-provided description. Descriptions that could be interpreted as formulas receive a leading apostrophe. |

Use settlement status when reconciling booked amounts. A failed or pending outgoing payment
still has a requested amount. An internal transfer appears in each participating wallet with its
own transaction ID and direction. Subsequent status changes appear on the original row when
you export again. SwissKnife exports the currently retained records, so a previously deleted
expired invoice or failed payment will no longer appear.
