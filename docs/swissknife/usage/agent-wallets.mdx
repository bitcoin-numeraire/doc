Use a dedicated credential when a tool needs access to one wallet. The owner chooses which operations it can perform and when it expires. An ordinary account credential represents the whole account.

## Grant wallet access

While signed in as the owner, send a `POST` to `/v1/me/wallets/{wallet_id}/agent-keys`. Supply a name, an RFC 3339 expiry within the next 365 days and at least one capability.

```json
{
  "name": "Billing assistant",
  "expires_at": "2026-12-15T12:00:00Z",
  "capabilities": { "read": true, "receive": true, "spend": false }
}
```

Choose a future expiry for your installation. The response includes the credential ID and a one-time secret beginning with `swka_`. Store that secret in your tool’s secret configuration. List credentials at the same URL with `GET`. To revoke one, send `DELETE /v1/me/wallets/{wallet_id}/agent-keys/{key_id}`.

A client sends the secret in the `Wallet-Key` header on a supported wallet route. Read permission allows wallet information, balances, contacts, invoices, payments, quotes and submission status. Receive permission creates invoices. Spend permission submits a durable payment for execution. Each request checks the wallet, capability, expiration and revocation state.

## Connect an MCP host

Start the command with an API origin and wallet UUID. Set `SWISSKNIFE_MCP_WALLET_KEY` in the child process environment through your host’s secret configuration.

```shell
swissknife mcp --server https://wallet.example.com --wallet 11111111-2222-4333-8444-555555555555
```

The host communicates with the command over standard input and output. Use an HTTPS origin for a remote instance or HTTP on loopback for local development. Start a separate command for each wallet.

The host discovers balance, wallet information, contacts, invoice creation and decoding, recent payments, payment submission and status tools. It can also read `wallet://balance` and `wallet://payments/recent`. Use decimal strings for exact millisatoshi values, including fees.

For a payment, approve the destination, principal and maximum fee. Save the submission UUID with those terms before calling the tool. A retry with the same UUID and terms returns the original submission. Read its status until settlement or a terminal failure. An accepted submission can still be pending. Invoice creation creates another invoice on each call.

## Set an account spending budget

Open an account in **Admin → Accounts** and select **Set spending limits**. Enter a per-payment, daily, weekly or monthly limit in sats, with up to three decimal places. A blank field leaves that period unrestricted. Zero blocks positive payments. Use a separate account for each agent that needs an independent budget. All wallets owned by one account draw from the same limits.

The dashboard offers three example templates in sats. Choosing one fills the form. Review the amounts, edit individual limits as needed, and select **Save limits** to apply them. Closing the editor discards your changes.

| Template | Per payment | Per agent in a rolling hour | Daily | Weekly | Monthly |
| --- | ---: | ---: | ---: | ---: | ---: |
| Conservative | 10 | 30 | 100 | 500 | 2,000 |
| Moderate | 50 | 150 | 500 | 2,500 | 10,000 |
| Generous | 100 | 300 | 1,000 | 5,000 | 20,000 |

The operator needs account write permission to change limits and account read permission to inspect usage. Give the agent a wallet credential. Keep the operator credential outside its process.

The API accepts decimal **millisatoshi strings** at `PUT /v1/accounts/{account_id}/spending-policy`. This example limits a single payment to 100 sats and the entire day to 1,000 sats.

```json
{
  "per_payment_msat": "100000",
  "daily_msat": "1000000"
}
```

Read limits and current usage with `GET` on the same URL. A missing or disabled policy returns HTTP 404. A payment that would exceed a limit returns HTTP 422 before dispatch. Its reservation includes the maximum fee. Settlement replaces the reservation with the actual amount and fee. Failure or cancellation releases the reserved budget. If a provider later confirms a payment, SwissKnife records the actual debit.

Calendar usage uses exact decimal millisatoshi strings, even when repeated payments take the total above the maximum value of a single payment. The day and month begin at midnight UTC. The week begins on Monday. A payment counts against the periods in which the wallet first accepted it, including when its settlement arrives in a later period. Retrying the same submission leaves usage unchanged. Incoming funds and administrative credits do not consume the budget.

Set **Per agent in a rolling hour** to limit each delegated wallet credential independently. For example, a 10-sat limit lets a credential spend 6 sats and then 4 sats. Further positive payments must wait until an earlier charge falls outside the preceding 60 minutes or a reservation releases funds. A second credential has its own hourly allowance. Direct owner payments still use the account-wide limits. To configure the same control through the spending-policy API, send `agent_hourly_msat` as a decimal string alongside the account limits you want to retain.

Disabling the budget lets new payments proceed without enforcement. Re-enabling it retains previously charged usage in the current periods. Payments admitted while it was disabled are outside that budget. Roll out the enforcing server version to every instance that can submit a payment before enabling a production policy.

## Compare agent activity

In **Admin → Accounts**, open the account and inspect **Agent spending activity**. The view refreshes every 30 seconds while visible. Compare the last 60 minutes with the preceding 60 minutes for each credential that had an admission in either window. Amounts include fees and outstanding reservations. Failed or released reservations can reduce the amount while the original admission still contributes to the payment count.

To flag unusual spending, set **Hourly warning per agent** in the account spending limits. For example, with a 500-sat warning, a credential at exactly 500 sats has no flag. One more millisatoshi shows **Above hourly warning threshold** beside its current-hour total. Payments continue under the usual limits. The flag clears when charges fall back to the threshold or below, including when a reservation is released or a payment ages out of the hour.

The spending-policy API accepts `agent_hourly_warning_msat` as a decimal string. Use `"500000"` for the example above, or `"0"` to flag any positive charge. You can use a warning on its own. Include the warning when replacing the policy to retain it. Each credential in the activity response has an `above_hourly_warning` boolean.

For the same data, use account read permission with `GET /v1/accounts/{account_id}/agent-spending-activity`. The response includes the UTC observation time, wallet and credential IDs, and separate payment counts and exact decimal millisatoshi amounts for both hours. The ending instant belongs to the window and its starting instant belongs to the preceding window. The page defaults to 25 credentials. To continue, pass `next_after` as `after`. You can request between 1 and 100 credentials with `limit`. Each call observes the current time.

Revoking a credential preserves its historical activity under the original ID. Owner payments and submissions outside an enabled spending policy are excluded. A review request first appears in spending activity when the payment is admitted.

## Review larger delegated payments

Set **Require approval above** in the account spending limits, or include `approval_above_msat` in the spending-policy PUT. The API accepts a decimal string in millisatoshis. The threshold compares the principal plus the maximum fee. A charge exactly equal to the threshold proceeds under the usual limits. Zero requires review for every positive delegated payment. Include the threshold when replacing the policy to retain it.

If review is required, the submission returns HTTP 409 with `code: "payment_approval_required"` and a `Location` header pointing to the operator’s review resource. At this stage, the payment has reserved zero funds. The original agent should retain the request body and its idempotency key.

In **Admin → Accounts**, open the paying account and select **Review payment** under **Payment approvals**. Compare the original request, resolved destination, wallet credential, principal, maximum fee, and total exposure. Choose **Approve retry** or **Reject**. The queue refreshes while the account is open.

1. Read `GET /v1/accounts/{account_id}/payment-approvals` with account read permission. Inspect the original input, resolved payment hash or Bitcoin address, wallet, credential, amount, and maximum fee.
2. Use account write permission to send `PUT /v1/accounts/{account_id}/payment-approvals/{id}` with `{"decision":"approve"}` or `{"decision":"reject"}`. An approval authorizes one retry from the same credential. The operator's decision, identity and timestamp are available at the same URL.
3. Retry the original payment submission. The wallet uses the reviewed invoice or Bitcoin destination, checks the credential, invoice expiry, balance and current spending rules, and admits the payment once. A revoked credential or rejected request cannot spend. A tighter budget may block the retry while the approval is still valid.

A review lasts up to 24 hours and ends sooner if the credential or a BOLT11 invoice expires. BOLT12 invoice expiry is checked again on admission. Core Lightning also expires an offer’s outstanding invoices when its issuer disables the offer. A subsequent provider failure releases the reservation. Each account can have up to 100 outstanding reviews, including approved requests awaiting retry. New request IDs start independent submissions. A wallet owner can still submit directly under the account limits.
