Use a dedicated credential when a tool needs access to one wallet. The owner chooses which operations it can perform and when it expires. An ordinary account credential represents the whole account.

## Grant wallet access

While signed in as the owner, send a `POST` to `/v1/me/wallets/{wallet_id}/agent-keys`. Supply a name, an RFC 3339 expiry within the next 365 days and at least one capability.

```json
{
  "name": "Billing assistant",
  "expires_at": "2026-12-15T12:00:00Z",
  "capabilities": { "read": true, "receive": true, "spend": false }
}
```

Choose a future expiry for your installation. The response includes the credential ID and a one-time secret beginning with `swka_`. Store that secret in your tool’s secret configuration. List credentials at the same URL with `GET`. To revoke one, send `DELETE /v1/me/wallets/{wallet_id}/agent-keys/{key_id}`.

A client sends the secret in the `Wallet-Key` header on a supported wallet route. Read permission allows wallet information, balances, contacts, invoices, payments, quotes and submission status. Receive permission creates invoices. Spend permission submits a durable payment for execution. Each request checks the wallet, capability, expiration and revocation state.

## Connect an MCP host

Start the command with an API origin and wallet UUID. Set `SWISSKNIFE_MCP_WALLET_KEY` in the child process environment through your host’s secret configuration.

```shell
swissknife mcp --server https://wallet.example.com --wallet 11111111-2222-4333-8444-555555555555
```

The host communicates with the command over standard input and output. Use an HTTPS origin for a remote instance or HTTP on loopback for local development. Start a separate command for each wallet.

The host discovers balance, wallet information, contacts, invoice creation and decoding, recent payments, payment submission and status tools. It can also read `wallet://balance` and `wallet://payments/recent`. Use decimal strings for exact millisatoshi values, including fees.

For a payment, approve the destination, principal and maximum fee. Save the submission UUID with those terms before calling the tool. A retry with the same UUID and terms returns the original submission. Read its status until settlement or a terminal failure. An accepted submission can still be pending. Invoice creation creates another invoice on each call.

## Set an account spending budget

Open an account in **Admin → Accounts** and select **Set spending limits**. Enter a per-payment, daily, weekly or monthly limit in sats, with up to three decimal places. A blank field leaves that period unrestricted. Zero blocks positive payments. Use a separate account for each agent that needs an independent budget. All wallets owned by one account draw from the same limits.

The operator needs account write permission to change limits and account read permission to inspect usage. Give the agent a wallet credential. Keep the operator credential outside its process.

The API accepts decimal **millisatoshi strings** at `PUT /v1/accounts/{account_id}/spending-policy`. This example limits a single payment to 100 sats and the entire day to 1,000 sats.

```json
{
  "per_payment_msat": "100000",
  "daily_msat": "1000000"
}
```

Read limits and current usage with `GET` on the same URL. A missing or disabled policy returns HTTP 404. A payment that would exceed a limit returns HTTP 422 before dispatch. Its reservation includes the maximum fee. Settlement replaces the reservation with the actual amount and fee. Failure or cancellation releases the reserved budget. If a provider later confirms a payment, SwissKnife records the actual debit.

The day and month begin at midnight UTC. The week begins on Monday. A payment counts against the periods in which the wallet first accepted it, including when its settlement arrives in a later period. Retrying the same submission leaves usage unchanged. Incoming funds and administrative credits do not consume the budget.

Disabling the budget lets new payments proceed without enforcement. Re-enabling it retains previously charged usage in the current periods. Payments admitted while it was disabled are outside that budget. Roll out the enforcing server version to every instance that can submit a payment before enabling a production policy.

## Connect over Streamable HTTP

For an MCP client on another machine, run a dedicated wallet connection bound to loopback. Set `SWISSKNIFE_MCP_WALLET_KEY` on the SwissKnife MCP host and generate an independent 32-byte secret with `openssl rand -hex 32` for `SWISSKNIFE_MCP_HTTP_TOKEN`.

```sh
swissknife mcp --server https://wallet.example.com \
  --wallet 89b4741a-62d3-4849-a848-79396f2ad427 \
  --http-listen 127.0.0.1:8452
```

Use a private tunnel to the loopback listener, or terminate HTTPS at a reverse proxy and pass `--public-origin https://mcp.example.com` to the same command. Forward the exact `/mcp` path and the public Host, preserve `Authorization`, and disable buffering for event streams. The client configures a Streamable HTTP endpoint and sends `Authorization: Bearer <transport-token>` on each request. Store the token in the client's secrets configuration.

The transport token grants access to this single wallet connection. Its tools use the wallet credential on the server, so revocation, expiry, payment approvals required by the client, and account spending limits continue to apply. For independent accounts or distinct permissions, configure separate endpoints and secrets. Rotate the transport token by restarting the MCP process. The default invocation continues to serve stdio.
